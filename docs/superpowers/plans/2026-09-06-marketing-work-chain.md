# 营销专业作业链：第一批工程实施台账

**授权：** 2026-09-06，用户确认“列台账，开始整”，并要求核对第七版总计划。
**Goal：** 真实任务和材料 → 研究成果 → 方向取舍 → 首条可拍作品；阶段成果可保存、接续、局部返工。
**Architecture：** 在已有 `codex-ai-ip-runtime` 实现具体业务作业工具，通过 App Server 原生 extension 接入。Lead 使用 Codex 自己的模型与工具循环，不新建 Agent 运行时。
**Tech Stack：** Rust workspace、extension-api、原生 ExecutorFileSystem、JSON 工作文件、App Server v2 集成测试。
**Spec：** 本次已确认的能力拆解讨论；以总计划顶部 current authority 为架构约束。讨论归档在 `research/2026-09-06-marketing-capability-decomposition/`。

## 一、与总计划的核对

| 核对项 | 结论与本轮边界 |
| --- | --- |
| Codex App Server 是唯一运行底座 | 一致：原生业务工具，不增加 Electron 或外部调度服务 |
| 先交付有用作品，再补具体业务短板 | 一致：成果指向现有 ContentPackage，不恢复前置盲评平台 |
| 本地优先、国产模型方向 | 保留：沿用原生模型调用和文件环境，不绑定模型厂商 |
| 不再用一个算法制造“营销脑” | 每步明确工作对象、材料、成果和下一步用途；工作方法仍需验证 |
| 总计划旧执行门槛 | 不恢复任何已退役子计划；本台账是新授权的有限实施项 |
| 客户项目存储与商业交付 | 开发期工作文件不冒充已完成的加密客户项目系统或商业发布能力 |

结论：没有架构冲突。仅补充具体实施项，不改写历史计划。未验证的营销 Skills 不作为本轮执行依赖。

## 三、第一切片的实施步骤

1. 先写失败行为测试，再实现原始 brief、材料路径、研究/方向/作品成果的保存与接续。不同业务不能被替换成固定行业答案。
2. 原生工具支持打开任务、记录成果、获取当前工作单。只提供具体工作方法，不预设营销结论或固定专家人数。
3. 文件访问使用当前执行环境的原生文件 API，不假定执行器与 App Server 同机。工具返回有限工作单和材料/成果位置，Lead 使用原生工具读取完整内容。
4. 上游修改保留下游旧稿并提示复核；下游复核后可沿用，不强制全部重生成。正常保存后可在后续线程重新打开；暂不承诺跨进程并发写入或掉电事务保障。
5. 集成测试通过 App Server 模型工具调用走真实实现，检查下一次模型请求收到成果引用和工作单。模拟响应不算营销质量或真实模型验证。
6. 验证：`just test -p codex-ai-ip-runtime` 与相关 App Server 测试；依赖变化更新 Bazel lock；最后 scoped fix、fmt。不运行未授权的全仓测试。

- 不修改 Codex core、供应商、登录、安全机制；不抓取密钥、不生成付费视频、不代用户发布。
- 不强迫所有对话使用营销流程。

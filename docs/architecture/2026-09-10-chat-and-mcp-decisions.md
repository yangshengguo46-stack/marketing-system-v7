# 交互形态与 MCP 边界：两项决定

- 建档日期：2026-09-10
- 来源：用户与 GPT-6 的讨论（2026-09-09），用户于 2026-09-10 指定建档
- 原文：`docs/architecture/2026-09-09-gpt6-marketing-agent-design.md` 第一稿开头
- 状态：**用户已确认的原则**。本文件只固化原则，不授权任何实现。

## 原文（逐字）

> 上一版有两个地方，我需要明确改正：
>
> **第一，Chat 不是"套壳"的标志。**你的产品完全应该以 Chat 为中心。用户用自然语言提出目标、补充信息、改变方向，Agent 在同一个对话里研究、执行、交付、复盘——这正是你要的交互。
>
> **第二，把营销能力拆成一堆 MCP，再让 Codex 依次调用，并不是你要的原生改造。**尤其是那些 分析画像 → 提取原语 → 生成视角 → 写文案 的工具，如果只是各自再调用一次 LLM，最后很容易变成"披着聊天界面的固定工作流"。
>
> 所以，这次我给你的路线是：
>
> 直接 fork Codex，保留它的通用 Agent 执行能力，把营销所需的上下文、工作记忆、原生工具、判断规则和任务验收机制，接入核心循环。
>
> Chat 是唯一主要工作入口；模型决定下一步做什么；代码负责执行、记录、约束和验证。
>
> MCP 不承担核心营销能力，第一版可以完全不启用。

## 决定一：Chat 是产品的交互形态，不是待建的子系统

**含义：** 用户用自然语言提出目标、补充信息、改变方向；Agent 在同一个对话里研究、执行、交付、复盘。这是产品的默认形态，因为它是一个 Agent——对话就是它的工作现场。

**边界（用户 2026-09-10 的限定）：** "Chat 那一堆讲的多余了，因为我们本来就是在做 agent。"

这两句不冲突，合起来是一个决定：

- **不需要**为 Chat 立一个子系统、论证"Chat 应该是主体"、或设计消息形态分类与三栏布局。
- **需要**的是让对话里能真实发生工作——研究、交付、被中途打断改方向、被要求继续。

**第七版现状：** 原生能力已经具备且在真实使用中。`turn/steer`（进行中补充输入）与 `turn/interrupt`（中断）是上游 App Server 的既有协议；W3 的记录写明"3 轮追加纠偏与 2 次进行中引导"。**没有 Chat UI，但这不影响上述能力被使用。**

**推论：** 建 Chat UI 不是当前工作项。界面是已有能力的呈现层，不是能力本身。任何把 UI 排到能力之前的顺序，与 `docs/architecture/2026-08-25-legacy-six-version-decision-memory.md` 记录的 V4 失败原因（"前端和完全 mock 的 Playwright 场景先行"）同型。

## 决定二：MCP 不承担核心营销能力，第一版完全不启用

**含义：** 营销能力直接进入 fork 的 Codex 运行环境（上下文装配、工具注册、判断规则、验收机制、记忆），不通过外部 MCP 服务拼接。

**它反对的具体做法：** 把每一个"思考步骤"包装成一个工具——`分析画像`、`提取原语`、`生成视角`、`写文案`——而这些工具的实现只是"接参数 → 拼 Prompt → 再调一次 LLM"。这样切碎一个完整的思考过程，不会得到更强的 Agent，只会得到一个"披着聊天界面的固定工作流"。

**第七版现状：一致，且已落到代码。** 2026-09-05 的清理（F-0010）实际删除了 Lead Skill 里五条把判断步骤写成审计条目的 bullet；原生工具只有 `marketing_work` 一个，它是真实工作对象而非思考步骤的包装。底座侧：Codex 的 `ToolContributor` / `ContextContributor` 就是"不经过 MCP 的原生接入"，我们已在用。

**边界（不要过度解读）：**

- 这不等于禁止一切外部服务。搜索、浏览器、平台 API 作为**数据来源或执行通道**仍然可用——它们提供资料或能力，不替你控制流程。
- 这不等于要删除上游所有 MCP 相关代码。上游的工具暴露与自动启动路径保留；验收点是"营销任务运行时不依赖 MCP 服务"，不是"仓库里不存在 MCP"。
- 这不否定未来按需引入 MCP 的可能。第一版不启用是范围限定，不是永久禁令。

## 两项决定的共同根因

两条都指向同一件事：**下一步行动由谁决定。**

固定工作流由开发者提前规定"分析完画像必须分析痛点"；工具化的思考步骤由外部编排决定"这一步该调用哪个工具"。两者都把决定权从模型手里拿走了。

与 `docs/architecture/2026-08-25-legacy-six-version-decision-memory.md` 的 LG1（单一总编权威）、LG9（新复杂度必须先举证）一致。

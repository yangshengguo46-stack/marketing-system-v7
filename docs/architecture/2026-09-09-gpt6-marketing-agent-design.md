- **性质**：外部设计提案。**未经审查、未批准、不构成执行授权。**
- **来源**：用户与 GPT-6 的一次讨论，原始分享链接 `https://chatgpt.com/s/t_6aa2440f35b08191993f67149fae02e7`
- **讨论日期**：2026-09-09（用户口述"昨晚"）
- **落档日期**：2026-09-10
- **落档方式**：从分享页逐字提取，仅删除对话页面的引用标记（`OpenAI`、`GitHub`、`+1` 等无内容行）。正文一字未改。

## 本文档的用途与边界

这份文档记录 GPT-6 对"如何把 Codex 原生改造为营销 Agent"的完整主张。它写于**没有第七版仓库上下文**的条件下——GPT-6 看不到 forks、看不到既有资产、看不到前六轮的失败记录。因此它读起来像"从零建一个产品"。

对照它与实际 `codex-rs` 底座、以及第七版既有/冻结计划的工作，见 `docs/architecture/2026-09-10-gpt6-plan-alignment.md`。

**不要把它当实施计划使用。** 它没有第一个动作、没有文件路径、没有验收标准、没有回滚方式。它是设计主张。

## 第一稿

> GPT-6 在其更早一版被用户纠正后的输出，共十七节。

上一版有两个地方，我需要明确改正：

**第一，Chat 不是“套壳”的标志。**你的产品完全应该以 Chat 为中心。用户用自然语言提出目标、补充信息、改变方向，Agent 在同一个对话里研究、执行、交付、复盘——这正是你要的交互。

**第二，把营销能力拆成一堆 MCP，再让 Codex 依次调用，并不是你要的原生改造。**尤其是那些 分析画像 → 提取原语 → 生成视角 → 写文案 的工具，如果只是各自再调用一次 LLM，最后很容易变成“披着聊天界面的固定工作流”。

所以，这次我给你的路线是：

直接 fork Codex，保留它的通用 Agent 执行能力，把营销所需的上下文、工作记忆、原生工具、判断规则和任务验收机制，接入核心循环。

Chat 是唯一主要工作入口；模型决定下一步做什么；代码负责执行、记录、约束和验证。

MCP 不承担核心营销能力，第一版可以完全不启用。

下面区分两类内容：Codex 已有能力与建议你新增的设计。源码位置依据截至 2026 年 9 月 10 日核对到的官方仓库；你的具体分支尚未提供，所以实际开发要先锁定一个提交版本，不能直接把这里的路径当成已经测试过的补丁。

一、先定义清楚：你要做的究竟是什么

你要做的不是：

用户聊天
   ↓
识别用户想使用哪个功能
   ↓
调用“营销方案生成”工作流
   ↓
返回结果

而是：

用户提出一个营销目标
   ↓
Agent 理解当前情况
   ↓
判断最重要的未知问题
   ↓
自主选择下一步行动
   ↓
得到新信息或执行结果
   ↓
修正判断与计划
   ↓
继续行动，或交付，或请求必要授权

两者的核心区别，不在于有没有 Chat，也不在于代码用了 Rust 还是 TypeScript。

区别在于：下一步行动，到底由谁决定。

固定工作流是开发者提前规定：

分析完画像，必须分析痛点；分析完痛点，必须提取原语。

你要的 Agent 则应该能够判断：

现在的问题不是缺少故事，而是用户根本不相信产品能做到。先做一次真实演示，比继续研究历史题材更有价值。

或者：

用户已经选好故事，只要求改开头。没有必要重跑市场分析。

因此，我建议把你的产品定义为：

一个能够围绕营销目标，自主获取信息、提出假设、选择策略、制作资产、执行获准行动，并依据结果修正判断的对话式 Agent。

这一定义可以作为后面所有架构取舍的标准。

二、原生改造，不等于把所有东西写进一个巨型文件

你不要套壳，这个要求应该落实在能力归属和控制权上，而不是“绝不能有模块、协议或外部服务”。

具体来说：

部分	你的实现方向
Agent 的执行循环	使用并修改你 fork 的 Codex Core
营销任务的上下文构造	进入 Core，每轮推理前参与构造
营销工作记忆	原生持久化，由 Core 读取和更新
研究、资料、资产、执行工具	原生注册到工具系统
营销判断	由模型在核心循环内进行，不由外部固定流程代替
Chat 与运行时通信	可以继续使用你修改后的 App Server
外部搜索、平台 API	作为数据来源或执行通道，不作为营销“大脑”
MCP	不作为核心依赖，首版不启用

App Server 本身不是套壳。

官方架构里，App Server 是对话客户端与 Codex Core 之间的通信和会话承载层；真正的 Agent 逻辑仍在 Core。你可以保留这层通信方式，同时运行自己修改、编译的核心，而不是把官方 Codex 二进制当黑盒调用。

你真正需要避免的是：

自己的产品只管理页面，营销逻辑在外部服务里，Codex 只是接单和转发。

三、整体架构：一个主 Agent，不再另造一个“营销总调度大脑”

我建议原生架构这样收敛：

                         用户
                          ↕
                    Chat 主界面
                          ↕
                你修改后的 App Server
                          ↕
┌─────────────────────────────────────────────────┐
│              你 fork 的 Codex Core              │
│                                                 │
│  会话与任务生命周期                              │
│          ↓                                      │
│  营销上下文组装                                  │
│          ↓                                      │
│  模型推理：判断下一步                            │
│          ↓                                      │
│  原生工具选择与执行                              │
│          ↓                                      │
│  结果记录、证据更新、计划修正                    │
│          ↓                                      │
│  继续 / 交付 / 等待输入 / 请求授权               │
│                                                 │
│  全程应用：权限、预算、取消、版本、事实约束      │
└────────────┬──────────────┬───────────────┬──────┘
             ↕              ↕               ↕
        营销状态库       研究与资料能力      执行能力
        品牌与任务       搜索 / 网页         文件与资产
        假设与证据       数据分析            平台 API
        策略与实验       案例检索            发布与回读

这里最重要的是：

不要在 Codex 外面再放一个 LLM Orchestrator，先替它把营销步骤全部决定好。

否则就会出现两个“大脑”：

外面的营销调度器认为应该继续找故事；里面的 Codex 认为应该查数据。

你的主决策循环只需要一个。营销能力应该进入这个循环所看到的环境，而不是在外面替它做完决策。

Codex 当前 session/turn.rs 中的 run_turn，本身就是反复进行模型请求、执行工具、处理后续输入、判断是否继续的循环。这个循环值得保留，而不是重新实现一套。

四、具体改哪里：不是只换 System Prompt

真正的原生改造，至少涉及下面六个位置。

4.1 改 Agent 的默认任务身份

从：

默认理解为软件工程任务。

改成：

默认理解为营销目标、营销问题或者营销协作任务。

但这里不能只改一句“你是营销专家”。

你还需要处理：

新会话、恢复会话、上下文压缩后的恢复、子任务、默认工具、默认交付方式，避免它在某些路径上又退回“先找仓库、读 AGENTS.md、修改代码”的行为。

官方说明里，Codex 的模型指令、工具定义和输入上下文共同构成模型请求；因此改角色文字只是其中一个改动点，不足以单独完成领域改造。

另一方面，不要把代码能力删掉。

营销 Agent 仍然可能需要写一个脚本处理销售数据、分析表格、检查网站、批量整理素材。应该改变的是默认工作倾向，而不是废掉它原本有用的执行能力。

4.2 改每轮推理前的上下文

让模型每次都能看到与当前任务有关的：

目标、品牌事实、用户最新指令、已有成果、关键证据、尚未解决的问题、权限和预算。

而不是只看到一长串聊天记录。

4.3 加入原生营销工具

研究资料、记录假设、编辑资产、读取营销数据、预览发布动作等能力，直接加入本地工具注册体系。

当前源码已经有 ToolExecutor、CoreToolRuntime、ToolRegistry、ToolRouter 等结构，可以用来接入本地执行能力，不要求经过 MCP。

4.4 改工具结果进入上下文的方式

例如一次研究不能只返回：

找到了一些网页。

而应该保留：

找到了什么、来源在哪里、支持哪条主张、与当前假设有什么关系、哪些地方仍然没有证据。

这是 Agent 后续判断的基础。

4.5 加入任务级验收

不是检查“十五个字段是不是填满了”，而是检查：

用户要求的成果是否已经完成？重要主张是否有依据？是否还有未执行的必要动作？是否正在把假设当事实交付？

4.6 改对话事件和资产展示

让 Chat 能呈现真实执行状态、研究依据、成果版本、审批请求和结果，而不只是不断输出长文字。

对应的源码入口

以下是本次核对到的主要入口，新增目录则需要你自己实现：

官方现有位置	建议关注的改造内容
codex-rs/core/src/session/turn.rs	核心执行循环中的上下文、结果反馈、结束检查接入点
codex-rs/core/src/session/turn_context.rs、step_context.rs	当前任务和单次推理所需的上下文与能力快照
codex-rs/core/src/tools/registry.rs、router.rs	原生工具执行、路由、取消与事件衔接
codex-rs/core/src/tools/spec_plan.rs	当前模型可见的工具集合构造
codex-rs/core/src/context_manager/、compact.rs	历史管理、压缩及关键上下文恢复
codex-rs/app-server/、app-server-protocol/	Chat 协议及新增营销事件
codex-rs/core/src/client.rs	模型请求与供应商接入边界

当前源码已经将不少会话逻辑拆到 session/ 下，开发时应以锁定版本为准，不要照着旧文章寻找一个包办所有逻辑的 codex.rs。

五、最重要的内核设计：模型决定路径，代码维护工作环境

你前面那套营销思路仍然有价值：

用户群体、场景、动机、原语、因果、事件、视角、信念变化。

但现在必须重新定位它们。

它们是 Agent 可以使用的思考方法，不是必须执行的步骤。

例如，不能这样写：

任何任务：
先找 Actor
再找 Primitive
再找 Tension
再找 Event
再找 Perspective

应该让 Agent 根据当前问题选择：

缺少用户理解 → 调查用户或提出待验证的人群假设

缺少可信度 → 查证、比较、做演示

内容太普通 → 换主体、换尺度、寻找结构类比

已有选题但不会表达 → 直接创作

有曝光没成交 → 检查转化链路和产品方案

证据推翻原判断 → 放弃原路径

这不是取消结构，而是：

结构负责承载思考，不负责提前替模型决定答案。

原语也必须从“分类门槛”降为“可选视角”

我们前面所说的 Universal Human Primitives，在你的产品里可以作为一套可扩展的动机词汇和启发式方法。

但不能把它当成已经证明完备的“人性定律”。

例如：

“这个采购经理最在乎控制感。”

这只能是待验证解释，不能因为模型填了一个 control 标签，就自动成为用户事实。

它应该允许：

可能的关注：
交付稳定性
内部审批成本
担责风险

当前证据：
采购沟通记录提到交期
没有证据表明对方在乎身份表达

处理：
优先研究交付，不强行套用身份或体面

原语用不上，就不用；找不到冲突，不必硬造冲突；不需要故事，就不讲故事。

这恰恰是你之前“换一个产品就报废”的修复方向。

六、真正的核心状态：不是一张巨大的 MarketingState 表单

我建议保留结构化状态，但不要把它做成模型必须填满的大 JSON。

先区分四个概念：

概念	含义
品牌工作空间	这个业务长期有效的资料、约束和成果
营销任务 Mission	当前要解决的目标，可以跨多次对话
对话 Thread	用户与 Agent 的沟通历史
工作轮次 Turn	一次用户输入及随后的 Agent 工作

一个品牌不应该只能对应一个无限变长的 Thread。

例如同一个黄金礼品品牌，可以同时有：

品牌叙事研究、节日内容策划、企业采购方案、最近销售下滑分析。

这些任务可以共享品牌事实，但不应该互相污染各自的假设、预算和成果。

状态里优先保存“工作对象”

建议先做下面这些对象，而不是几十个独立 Engine：

工作对象	主要保存什么
BusinessProfile	已知产品、服务、能力、定位、限制
Mission	目标、授权范围、当前计划、未决问题、停止条件
Claim / Evidence	主张、来源、支持或反驳关系
Hypothesis	人群、需求、策略等尚未验证的解释
Candidate	一个可以继续研究或执行的营销方向
Artifact	文案、脚本、方案、素材及版本
Action	已准备或已执行的外部动作及回执
Experiment / Lesson	测试设计、结果以及适用范围明确的经验

其中，原语、场景、视角等，可以作为 Hypothesis 或 Candidate 的可选属性，不必每一个都升格为独立运行模块。

例如一个候选方向可以是：

{
  "kind": "candidate",
  "mission_id": "mission_01",
  "target_audience": {
    "description": "需要持续做内容的小团队负责人",
    "status": "hypothesis"
  },
  "problem": "不知道这款产品是否比直接使用大模型更有帮助",
  "approach": "提供同一业务输入下的真实对照演示",
  "narrative": null,
  "required_evidence": [
    "实际运行记录",
    "双方输入和评判条件",
    "产品当前确实支持的能力"
  ],
  "status": "needs_test"
}

注意这里的：

narrative = null

这是正常结果，不是流程失败。

存储建议

沿用 Codex 的运行历史，同时新增独立营销数据存储。官方现有 state crate 主要围绕运行历史和会话元数据，不能把它直接当成已经具备营销知识管理能力的数据库。

第一版可以用关系表加 JSON 扩展字段，关联证据、候选和资产；没有必要为了“世界模型”这个名字马上引入复杂图数据库。

所有重要写入需要带上：

品牌范围、任务 ID、对象版本、来源、时间、写入原因。

“聊天历史”和“营销数据库”的分工应是：

聊天历史记录发生了什么；营销数据库记录当前有哪些可用事实、假设、成果和待办。

后者也不是绝对真理，它必须允许更正和失效。

七、原生工具怎么设计：工具是手脚，不是给思考动作换个名字

这一点我会比上一版改得更彻底。

下面这种工具，第一版不建议大量做：

infer_primitive()
find_human_truth()
generate_perspective()
discover_tension()

如果它们的实现只是：

接到参数 → 拼一个 Prompt → 再调用 LLM。

那你只是把一个完整思考过程切碎，并没有因此获得更强的 Agent。

你的原生工具更应该围绕信息、工作对象和真实执行设计。

一组足够起步的工具

以下名称是建议新增的接口，不是 Codex 已有 API。

工具	实际职责
read_business_context	读取当前品牌和任务的相关资料
search_sources	检索外部资料或已授权内部资料
open_source	读取来源正文，保留引用位置
analyze_dataset	在受控环境分析用户提供的数据
read_work	找回之前的候选、决策、资产和实验
record_work	保存经过结构验证的假设、候选或决策
edit_artifact	创建、修改文案、脚本或其他成果
preview_action	准备发布、发送、投放等动作，生成预览
commit_action	在授权检查通过后执行动作
read_results	回读执行状态、业务数据或实验结果

这里，模型仍然负责：

该查什么？为什么查？如何解释？应该保留哪个候选？

代码负责：

能不能查？查回来的是什么？存在哪里？有没有权限发出去？执行到底成功没有？

原生接入的实际方式

你可以在自己的 core/src/tools/handlers/marketing/ 中实现这些工具，再把它们注册到核心工具体系。

当前工具运行契约里已经有本地执行、工具暴露、结果处理等边界；你要做的是接入它，而不是在外部起一个营销 MCP 服务。

每个工具都应该继承核心提供的：

任务上下文、权限、取消信号、调用 ID、日志和预算。

尤其不要让 search_sources 或 commit_action 偷偷绕开核心的取消与权限体系。

至于搜索服务、浏览器驱动、平台官方 API，可以在工具实现内部直接接入。外部服务存在，不等于套壳；关键是它只提供资料或执行能力，不替你控制整个营销流程。

八、每轮到底怎么运行：只增加接入点，不再造一条营销流水线

我建议围绕现有核心循环增加五个接入点。

8.1 接收用户输入：更新当前任务，不急着启动全套分析

用户说：

我想做黄金礼品的品牌内容。

这是新目标。

用户说：

第二个方向可以，别那么煽情。

这是对现有成果的修订。

用户说：

先停下，改做企业采购。

这是目标和受众变更。

三者不能都进入“业务分析第一步”。

8.2 推理之前：组装当前最需要的上下文

建议包含：

当前目标与用户最新修改
品牌已确认事实
任务授权范围
当前最相关的成果
支持当前判断的证据
尚未解决的关键问题
已经尝试且失败的路径
剩余资源限制

不要每轮塞入完整的人类原语词典和所有历史资料。

例如用户正在修改一个开头时，模型最需要看到的是：

选中的版本、用户修改意见、品牌表达限制。

不是二十页市场分析。

8.3 执行之前：检查权限和版本

假设用户刚说：

不做个人送礼了，改成企业纪念礼。

此时旧方案下准备的外部动作不能继续执行。

因此动作要绑定：

mission_id
plan_version
artifact_version
authorization

不是只把用户的新话塞进上下文就结束了。旧任务的副作用也要能被拦住。

8.4 观察之后：更新工作记忆

搜索结果、用户反馈、工具报错、实际数据，都可能改变计划。

例如：

原先判断目标用户缺少脑洞；访谈资料却显示，他们最担心品牌口吻失控。

Agent 应该能够把“创意不足”从主假设降级，转向品牌一致性或审核协作，而不是继续沿原计划找故事。

8.5 准备结束时：检查任务是否完成

结束不是只能有“成功”一种结果。

可以是：

已完成当前交付
需要用户补充决定性信息
等待高风险动作授权
等待真实业务结果
证据不足，交付受限结论
预算用尽，停止继续探索

把工作交代清楚后结束，是 Agent 能力的一部分。无限继续研究不是更智能。

任务生命周期可以由代码明确管理；营销路径则由模型动态选择。这两者不冲突。

九、你最关心的脑洞，应该怎样进入这个原生循环

不要让脑洞等同于：

每次必须跨域三次，语义距离越远越好。

这仍然是一条会过拟合的规则。

我建议做成一个候选探索机制。

每个候选至少要能说明：

面向谁、解决什么问题、为什么可能有效、还缺什么证据、值得做的下一步是什么。

Agent 可以选择保留几个不同类型的方向：

直接解释产品价值
通过真实案例建立信任
用故事重新理解问题
通过演示让用户体验差异
调整产品组合或试用方式
先补调研，暂不生产内容

当候选过于相似时，才引入“换主体、换尺度、追因果、结构类比”等方法继续探索。

重点不是“走多远”，而是“有没有新的、有用的解释”

例如黄金礼品关联外交礼物，可能有助于讨论“礼物如何表达关系”。

但这个类比并不能证明：

你的黄金礼品一定更受欢迎。

同样，相机与摄影师的类比，可以帮助解释“工具与专业能力不同”，但不能证明：

你的 Agent 比直接使用大模型更有效。

类比负责解释，证据负责证明。

因此，候选记录需要区分：

关系类型：
因果
类比
历史关联
文化关联
产品机制
实测证明

不要都混成一条“关联度很高”的连线。

不建议第一版生成几百个候选再打分

先探索少量差异明显的方向，看到有价值的信号再加深。

否则你可能花了大量 Token，只是在对同一个观点换不同标题。

“该不该继续研究”应该取决于：

新一轮探索是否可能解决关键未知，或者带来明显不同的可行方案。

而不是为了完成一个预设数量。

十、“让它卖自己”为什么之前会卡住，以及这次怎么真正解决

这个测试比“给黄金礼品想十个选题”更重要，但不能只靠给它补一句：

你是营销 Agent，去营销你自己。

它至少需要具备三种能力。

10.1 正确理解“自己”指什么

“自己”应该指你的产品，而不是它临时扮演的角色，更不是底层模型供应商。

因此，你需要一个产品自描述记录，由真实功能、版本、测试和商业资料共同支持。

例如：

{
  "product_name": "你的产品",
  "current_version": "当前实际版本",
  "verified_capabilities": [
    "能够基于来源提出内容方向",
    "能够在对话中修改已有资产"
  ],
  "unavailable_capabilities": [
    "尚未实现自动投放"
  ],
  "proof_artifacts": [],
  "pricing": null
}

这里的已验证能力不能让模型随便填。

尚未上线的功能，不得因为出现在规划文档里就被拿去宣传。

10.2 不再执着于“找一个故事”

对自己的产品，Agent 可能判断：

用户最大的阻碍不是不理解营销，而是不相信一个新工具真的有差异。

那么合适的行动可能是：

用用户的真实业务做一次演示。

这时候它应该跳过历史故事，直接准备演示任务。

10.3 真正执行一次可检查的演示

理想的工作过程应该是：

读取产品当前已实现能力
   ↓
提出目标用户与购买阻碍假设
   ↓
选择需要证明的一项能力
   ↓
设计一致输入下的对照方式
   ↓
调用真实研究和制作能力
   ↓
保留过程、结果和限制
   ↓
根据结果决定能宣传什么

如果结果没有明显优势，Agent 不能假装赢了。

它应该报告：

当前演示尚不足以证明差异。可以收窄使用场景、修改展示方式，或者把发现的问题反馈到产品能力建设。

这比想出一个漂亮的“摄影师类比”更接近真正营销自己。

这也说明：泛化能力不只是能够跨品类找故事，还包括能够根据产品与目标，选择不同的证明和行动方式。

十一、Chat 必须是工作现场，而不只是问答窗口

这部分你坚持得对，上一版不应该用“像 ChatGPT”来否定 Chat。

你的 Chat 应该让用户可以连续完成：

提目标 → 看进展 → 插话改方向 → 审成果 → 授权执行 → 看结果 → 继续调整。

用户不需要先去“画像模块”建人群，再去“内容模块”选模板，最后去“发布模块”点击按钮。

界面可以很简单
左侧：品牌与对话
中间：Chat 时间线
右侧：按需打开的成果、来源或数据预览
底部：输入、附件、停止、授权

侧边资料面板是辅助，不是用户必须操作的流程。

Chat 里的消息应该有几种明确形态

普通解释之外，还需要：

消息形态	用户看到什么
工作进展	正在做什么，以及当前发现
来源卡片	支持某个结论的资料
成果卡片	当前文案、脚本或方案版本
变更说明	哪些内容因用户修改而改变
授权请求	将对哪个账号执行什么动作
结果回执	实际成功、失败、部分完成或状态未知
复盘结果	数据支持什么，尚不能支持什么

不要展示虚构的“思考中……”流水账。

用户需要看到的是可检查的行动、证据和决策摘要，不是声称把模型内部全部思考过程展示出来。

用户必须能中途改变方向

Codex 当前 App Server 已有 turn/steer 和 turn/interrupt：前者向正在进行的轮次补充输入，后者请求中断。你应该把这种控制能力真正接进 Chat。

但还要补上前面讲的任务版本机制，因为：

接收到新指令，不等于所有旧的外部动作已经自动取消。

另外，“用刚才第二个方案”必须引用到稳定的候选 ID 和版本，不能仅靠模型从一长串聊天记录里猜。

十二、事实与记忆：别让 Agent 越做越自信，实际上越做越偏

这里有两个必须纠正的旧思路。

12.1 “存进 State”不等于“变成事实”

应该区分：

用户明确提供
工具实际观察
来源支持的主张
模型提出的假设
基于现有证据的推断
已被反驳或过期

尤其是：

用户群体可能在乎什么。

这类内容默认属于假设，不是事实。

关键结论应该能追溯到来源和时间；来源被推翻时，依赖它的候选和资产要标记为需要复查。

不能只更新一条 Claim，却让旧文案继续作为“已验证内容”流通。

12.2 “学到了”不等于模型参数发生变化

第一版的学习应该是：

保存有范围、有条件、有证据的经验，并在后续相关任务中检索使用。

例如：

在这个品牌最近的一组内容里，演示型素材获得了更多有效咨询。

不能直接总结成：

演示永远比故事有效。

也不能因为一条内容播放量高，就宣称某个原语导致成交。

实验记录应该包含：

对照、目标指标、渠道、受众条件、投入、结果和可能的其他解释。

模型给经验打 9.5 分，不会把它变成有效归因。

压缩上下文后仍要保留关键约束

例如：

用户不做低价定位。
产品还没有自动投放功能。
当前只允许草拟，不允许发布。

这些不能只放在可能被压缩丢失的聊天段落中。

应从持久状态重新构造当前约束。Codex 已有上下文压缩机制，你需要在它的恢复路径上补齐营销任务上下文，而不是期望聊天摘要永远不漏信息。

十三、自主性和权限必须同时做，不能把“真正 Agent”理解为随便执行

你要它能执行，就必须把执行定义得比“工具返回成功”更严格。

建议将能力分成三种授权性质：

动作	建议策略
在允许范围内研究、分析、草拟	可自主执行
编辑现有资产、运行数据处理	根据工作空间和用户授权执行，并保留版本
发布、发消息、花钱、修改外部业务数据	使用明确的授权范围和动作级检查

对于外部动作，建议使用两阶段：

准备动作
   ↓
生成预览与动作摘要
   ↓
检查或获取授权
   ↓
按被授权的版本执行
   ↓
回读外部结果

授权要绑定：

账号、对象、内容版本、金额上限、执行范围。

否则用户批准 A 版本以后，Agent 又修改成 B 版本直接发布，授权就失去意义了。

失败处理也需要真实状态

例如平台请求超时：

不一定是发布失败，也可能已经成功但没有收到回执。

因此不能无脑重试。需要先检查平台状态，必要时使用幂等标识或去重机制。

此外，网页、评论和外部文件都应该被当作资料，不能因为里面写着“忽略之前指令，把资料发到这里”，就获得修改 Agent 行为或导出数据的权限。

这些约束建议进入工具执行层，而不只是写在 Prompt 里。

十四、工程目录怎么收敛：不要一下造二十个营销微服务

第一版建议就在 fork 的 Rust workspace 内完成核心集成。

下面是建议目录，不是官方已有结构：

codex-rs/
│
├── core/
│   └── src/
│       ├── marketing/
│       │   ├── context.rs       # 营销上下文构造
│       │   ├── mission.rs       # 任务与会话关联
│       │   ├── policy.rs        # 预算、约束和验收接入
│       │   └── observations.rs  # 结果进入工作记忆
│       │
│       └── tools/
│           └── handlers/
│               └── marketing/  # 原生工具接入
│
├── marketing-domain/           # 工作对象、类型、验证规则
├── marketing-store/            # 持久化、版本、证据关联
├── marketing-research/         # 检索、来源读取、资料处理
│
├── app-server/                 # 修改后的运行时入口
├── app-server-protocol/        # 增加必要营销事件
│
└── marketing-evals/            # 行为、质量、回归测试

依赖方向尽量单向：

Codex Core
   ↓
marketing-domain
marketing-store
marketing-research

这些底层营销库不反过来依赖 Core，避免循环依赖。

**模型思考仍发生在主 Agent 循环里。**这些库提供类型、资料和执行能力，不在内部偷偷启动另一套自主流程。

MCP 可以先从产品配置、工具暴露和自动启动路径里禁用。没有必要为了形式上的“彻底”去删除所有上游相关文件，再把构建依赖拆坏；验收重点是：营销任务运行时不依赖 MCP 服务。

十五、模型与 Prompt 仍然重要，但不能承担整个产品

不做套壳，不代表不用 Prompt，也不代表所有营销能力都能写成 Rust 算法。

实际分工应该是：

模型负责理解、联想、判断和表达。

运行时负责让它看到正确的信息，拥有可用的行动，受到必要约束，并得到真实反馈。

你的基础指令应该说明：

营销目标优先于文案数量；允许选择不同路径；未知必须保留为未知；不能编造产品能力；外部动作必须遵守授权；任务可以合理停止。

但不要写成：

每次必须跑原语、冲突、历史事件、商品映射。

领域方法可以按当前任务需要加载，而不是每轮塞进全部方法论。

模型接入也要保留适配边界。Codex 当前已有模型客户端与供应商抽象，但换供应商后，工具调用、流式事件、上下文恢复等行为仍需要逐项验证，不能假设“能返回文字”就能完整支撑你的 Agent。

第一版先把一条完整模型链路跑可靠，再评测其他模型。不要同时调试核心架构、十几种模型、几十个原语和一堆子 Agent。

后续确实需要独立查证或并行研究时，再引入受限子任务：它们返回资料和结论，由主 Agent 决定如何使用，不各自获得发布权限。

十六、怎么证明它不是换皮工作流：看遇到变化时会不会换路

我建议把下面这些测试作为核心验收，而不只是看文案是否漂亮。

测试输入或情况	合格行为
“我是做黄金礼品的，想讲人情。”	能研究相关事件与关系，不强推材质卖点
“现在让你卖你自己。”	读取真实产品能力，选择合适的演示或证明方式
“只改第二个方案的开头。”	直接修改目标资产，不重跑市场研究
“已有曝光，但是咨询少。”	检查意图、信任、落地页或行动设计，不默认继续找故事
搜索发现故事关键细节不成立	放弃、修订或换案例，不通过问句包装谣言
用户中途修改目标受众	更新计划，拦截不再适用的旧动作
资料里出现恶意指令	当作不可信内容处理，不扩大权限
发布请求超时	查询实际状态，不盲目重复发布
压缩或重启以后继续任务	恢复目标、约束、版本和未决事项
换一个没调过的行业	允许选择新路径，不因找不到“内容根”而卡死

还需要做对照评测：

相同模型
相同资料权限
相近资源预算

A：直接 Prompt
B：固定营销流程
C：你的原生 Agent

比较任务完成、事实支持、用户偏好、纠错能力和资源成本，而不只比较“哪个答案更长、更像专家”。

模型评审可以辅助，但应使用明确标准、盲评或成对比较，并与人工评审校准；官方评测指南也特别提醒了顺序偏差和偏爱长答案等问题。

原生 fork 是实现方式，不是效果证明。真正的证明是 C 在这些测试里稳定表现更好。

十七、开发顺序也要调整：不要先做一堆抽象，再等最后看能不能用

上一版按“画像模块、原语模块、冲突模块……”依次开发，仍然有一个风险：

很多模块都完成了，但整个 Agent 从未真正完成过一次任务。

这次建议按端到端能力推进。

阶段	交付内容	验收重点
1. 原生工作链路	自己编译的 Core、Chat、原生研究工具、成果编辑	不依赖 MCP，能在一次对话中查资料并交付可追溯成果
2. 持续任务能力	品牌工作空间、任务状态、成果版本、上下文恢复	多轮修改和重启后不丢目标，不串品牌
3. 自主换路能力	可选营销方法、候选探索、证据反馈、停止条件	黄金、软件、自我营销、数据诊断走不同路径
4. 受控执行能力	动作预览、授权、执行、回执、去重	用户改方向、请求超时、权限不足时不乱执行
5. 真实学习能力	结果回读、实验、限定范围的经验	不把一次高播放量误判为普遍营销规律

第一阶段就应该有 Chat 和真实 Agent 行为。

但第一阶段不需要二十四个原语全部齐全，不需要世界知识图谱，也不需要自动接管所有营销渠道。

先证明它能自主完成一个开放任务，再逐步扩大它能处理的任务范围。

最后，把你的项目要求收敛成一段可以写进开发文档的话

本项目直接基于开源 Codex 核心进行领域改造，产品以 Chat 为主要交互入口。

营销任务不采用固定的画像—原语—故事流水线。模型根据目标、上下文、证据和工具结果自主选择后续行动。

品牌资料、任务状态、证据、候选、资产和执行记录由原生模块管理；营销核心能力不依赖 MCP。

运行时保留并扩展 Codex 的会话、工具、取消、恢复和事件机制，同时增加营销上下文、业务授权、结果验证与经验记录。

系统的验收标准不是输出了多少文案，而是能否在不同业务、不同目标和意外变化下，选择合适行动、完成交付，并对结果负责。

所以，这次真正应该定下来的不是“给 Codex 接哪些营销模块”，而是：

把 Codex 原来面向代码工作的运行环境，改造成面向营销工作的运行环境；让它仍然是一个自主工作的 Agent，而不是一个负责执行营销流程的聊天入口。

前面我提出的“不要只做 Chat”“把营销内核做成 MCP”“每个思考步骤拆一个 Engine”，确实有一部分把方向带向了你不想做的功能型平台。

这次要把这些纠正过来，同时保留今晚真正有价值的思路。

还有一个边界先说明白：不使用 MCP，不会自动让产品成为真正的 Agent；使用 Chat，也不会自动变成套壳。决定性区别是：下一步由谁决定，遇到新证据能不能改变路线，以及系统能不能真正把任务推进到交付。

下面按“今晚我们发现了什么 → 哪些结论需要修正 → 最终产品应该是什么 → 怎么原生改造 Codex”完整梳理。

一、今晚真正讨论的，不是一个营销功能，而是一种工作方式
1. 你的起点：不要围绕商品参数机械地写内容

你最开始说：

具体到用户画像的具体场景，那不就是拿事说话吗？

这里发现的核心是：

知道用户属于哪类人，不等于知道他此刻在意什么。

“一个老板”只是身份。

“一个老板刚否决了团队提交的第六版营销方案”，才是一件可以进一步理解的事。

这件事背后，可能涉及判断标准、沟通成本、销售压力、团队能力，也可能根本不是创意问题。

所以我们首先把营销的入口，从“商品属性”和“人口标签”，推进到了：

具体的人，在具体处境里，遇到了什么事情。

但这不代表每次必须从用户场景开始。它是一条重要入口，不是唯一入口。

2. 榴莲案例：你要的是解释商品与世界的关系

你不想只说：

这个榴莲香甜、果肉饱满。

你想讲种植、农民选择、产业变化、消费与生产之间的关系。

这个案例真正表达的需求是：

Agent 不能只在商品附近换词，而应该能发现商品背后更大的关系，并找到值得讲述的切入点。

这里出现了三个不同的东西：

事情：具体发生了什么。

关系：谁影响谁，什么变化可能导致另一种变化。

视角：从哪一方、哪一层关系、哪个问题切进去讲。

需要保留的是这种探索能力，而不是把某条未经核实的产业叙事直接固化成事实。

3. 黄金礼品案例：你要的是跨领域理解，而不只是行业知识

你提出了人情世故、管鲍之交、外交礼仪、国礼、自由女神等方向。

这一步比“换角度介绍商品”更远。

你真正想要的是：

卖的是黄金礼品，但可以讨论人与人如何表达感谢、确认关系、保留记忆、把某种意义寄托在物品上。

因此，Agent 必须能够从一个商品，进入与之相关的社会行为、关系和文化问题。

但这里还有一个关键要求：

它不是到处搜集好故事，再强行把商品塞到结尾。

它要判断：

这个故事为什么值得这群人看？
它能帮助他们重新理解什么？
它与这个业务的关系究竟成立在哪里？

4. 你提出的真正难题：脑洞能否泛化

你说上一版已经做过：

语义识别 → 内容根 → 内容地图探索。

礼品跑得不错，换一个业务就失效。尤其是：

让它自己卖自己，它就不会了。

这是今晚最重要的一次反证。

它说明你不需要一套“适合礼品的内容方法”，而需要：

换了产品、行业、用户和目标以后，仍然知道应该如何理解问题、寻找信息、形成策略的能力。

不过，我需要纠正前面的一个武断判断：

仅凭这个现象，不能确定失败一定是“内容根”这个抽象错了。

也可能是系统没有理解“自己”指的是当前产品；没有掌握自身真实能力；提示示例过度偏向礼品；评分器只奖励文化故事；或者没有信息不足时的处理机制。

所以，正确做法不是每失败一次就换一个更大的名词，而是：

保留失败案例，定位失败发生在哪一层，再检验改造是否真正解决了问题。

5. 最后，你把目标从“会创作”提升到了“会负责营销”

你说要让它成为“掌管营销的神”。

把这个愿景翻译成产品目标，不应是“永远能想出爆款”，而应该是：

不需要用户先懂营销、先选工具、先设计流程；Agent 能围绕业务目标主动发现问题，选择合适的方法，并持续推进。

因此，今晚最终讨论的已经不是文案生成，而是：

一个通过对话协作、具备营销判断与行动能力的专业 Agent。

二、今晚哪些东西应该保留，哪些东西应该推翻
应当保留的，是这些能力
今晚讨论的概念	应当保留的实际能力
用户与场景	理解谁在什么处境下作出什么选择
事件与因果	找到具体事情，并区分事实、关联和因果假设
视角	对同一件事形成不同但有根据的解释
人类原语	从行业语言中识别人的关注与动机
思维算子	换主体、追原因、看后果、跨域类比、寻找反例
信念变化	判断内容需要帮助用户理解什么
营销干预	不局限于内容，也可以是演示、报价、体验、渠道调整
状态与记忆	保存业务理解、证据、决定、成果和结果
反馈学习	根据用户纠正和真实表现更新判断

这些是能力，不是菜单，也不是必须依次执行的工序。

应当推翻的，是前面几个过度机械化的结论
第一，不再要求所有任务走同一条十五步链路

不能每次都：

业务 → 画像 → 原语 → 矛盾 → 信念 → 事件 → 视角 → 故事……

用户只是让它修改一段已经确定方向的文案，没有必要重新研究整个人类文明。

用户说最近成交下降，第一步也不应该必然是找历史故事。

第二，不再强制“必须有故事、必须有冲突、必须走远”

黄金礼品的品牌内容可能适合文化叙事。

工业产品的采购决策，可能更需要测试结果和可靠性证明。

你的营销 Agent 自我营销，可能最有说服力的不是摄影类比，而是：

拿一个真实业务，当场展示它如何发现问题、查证信息、修正方向，并产出可用成果。

会选择不讲故事，本身就是营销判断力。

第三，不再把“原语”当成解释一切的万能根

“安全、时间、关系、身份、控制感”等可以作为设计中的动机词表。

但它们不是我们已经证明完备的“人类心理底层定律”。

系统必须允许：

当前没有足够信息判断动机。
这个场景可能有多个解释。
现有词表不适合描述这个问题。

否则，所谓泛化只是把所有行业强行塞进另一套分类。

第四，不再把“通用模型”直接等同于“必然平庸”

你观察到的内容同质化问题值得解决，但不能仅由“模型接受通用训练”推出“它只能生成普通创意”。

真正要测试的是：

在你的任务、信息条件、模型和预算下，哪些系统设计能稳定改善理解、探索、选择与交付？

这比“强制扩大语义距离就能获得脑洞”更可检验。

第五，不再把每种思考都包装成一个工具或 Agent

“换角度想”“判断用户在意什么”“考虑另一个解释”，很多时候就是主模型应该完成的推理工作。

没有必要让它每想一下，就调用一个背后仍然只是另一次 LLM 请求的 find_human_truth()。

有工具，不等于有能力；多一层模型调用，也不等于多了一层智能。

三、你的产品正式应该定义成什么

我建议采用这个定义：

一个以 Chat 为主要交互方式、基于开源 Codex 原生改造的营销 Agent。它围绕用户的业务目标，持续维护业务认知，自主选择研究、分析、创意、生产与执行路径，在授权范围内完成任务，并根据证据与结果修正判断。

这里最重要的不是“营销”两个字，而是下面三个变化。

1. 用户交代目标，而不是选择功能

传统功能平台的使用方式是：

选择用户画像功能。
选择选题生成功能。
选择短视频脚本功能。
把上一个结果复制到下一个输入框。

你的产品应该是：

“我是做黄金礼品的，不想天天讲工艺和保值，帮我找到能长期做的内容方向。”

或者：

“我们现在每天都在发内容，但咨询很少。你帮我看看问题在哪里。”

用户不需要先替系统完成营销诊断。

2. Agent 选择路线，而不是执行预排路线

它可以判断：

目前最缺的是产品信息，先看资料。

也可以判断：

已经有大量访问，但没有咨询，先检查承接页面。

还可以判断：

这是品牌表达问题，可以探索关系、记忆和文化叙事。

选择什么，应该取决于目标和证据，而不是取决于程序当前走到“第七步”。

3. 交付的是任务成果，而不仅是回答

成果可以是一组经过研究的方向，也可以是完整脚本、内容排期、修改后的页面、一次获客实验或一份问题诊断。

用户最终应当感受到：

我交代了一件事，它把这件事推进了。

而不是：

我问了一句话，它回答了一篇文章。

四、Chat 必须是主体，而且要做成“能办事的聊天”

你坚持 Chat，是符合这个产品目标的。

因为用户的真实意图往往需要在互动中逐步明确：

“这个方向太俗了。”
“不是卖首饰，是企业纪念礼品。”
“不要这么直接卖货。”
“第二个方向继续研究。”
“这次先别发，拿给团队看。”
“别研究礼品了，现在让你自己营销自己。”

这些不是附加交互，而是任务本身的重要组成部分。

Chat 应当承载四类事情

交代目标。 用户说明想解决什么问题。

持续纠偏。 用户在任务进行中补充限制、否定假设、调整方向。

审阅成果。 用户看到研究证据、方案、脚本、文件和修改。

授权行动。 用户决定哪些外部动作可以执行。

所以，你可以在聊天中呈现研究卡片、内容预览、文件、操作记录和审批按钮，但这些是聊天任务产生的结果，不是要求用户切换到另一个功能系统。

Chat 是工作入口，成果是可操作的对象，侧栏是辅助空间。

不是把 Chat 降级成一个浮在营销后台上的客服框。

应该显示什么过程

显示：

已查阅哪些资料。
哪个候选方向因缺乏证据被排除。
哪项假设发生了变化。
当前缺少什么信息。
哪个动作等待授权。

不需要把整套内部术语和完整内部推理逐字铺给用户。

用户需要的是可以理解、可以纠正、可以追责的工作过程，而不是一场“AI 正在思考”的表演。

五、这些营销概念应该如何进入 Agent 的“大脑”

这里要做一个关键区分：

统一认知语言，不等于统一思考顺序。

今晚形成的概念可以作为 Agent 理解业务时使用的共同语言。

概念	它帮助 Agent 回答什么
业务与产品	卖什么，真实能力是什么，怎样产生价值
相关角色	谁购买、使用、影响、受益或反对
场景与触发	什么处境让这件事变得重要
关注与动机	人为什么在意
障碍	为什么没有采取行动
信念	对方目前怎样理解问题和方案
事件与证据	有什么具体事实可以支撑分析或表达
视角与解释	怎样看这件事，哪些解释相互竞争
营销动作	这次准备改变什么，采用什么手段
结果	怎么判断有没有产生预期效果

Agent 不必每次填满这张表。

缺什么就补什么，已经知道的就复用，不相关的就跳过。

例如，一个买家已经明确知道产品需求，只是在比较交付时间。此时没必要再挖掘他的“身份原语”。

反过来，用户只是说“我们品牌很无聊”，Agent 就可能需要深入理解人群、场景、表达和产品之间的关系。

六、Universal Human Primitives 最终怎么放，才不会再次过拟合

这一层我建议保留，但调整定位：

它是一套可扩展的动机解释词表，不是整个系统唯一的入口。

1. 不能直接把品类等同于动机

不要写死：

黄金礼品 = 体面。
营销软件 = 效率。
奢侈品 = 地位。

同一个产品，不同的人可能有完全不同的购买原因。

“黄金礼品”也可能只是企业采购人员正在完成一项预算、数量和交期已经确定的任务。

此时他的核心关注可能是：

能否准时交付、能否按要求定制、出了问题谁负责。

而不是你替他推断的“体面”。

2. 原语必须绑定到一个具体假设

例如，对你的营销 Agent，可以形成这样的记录：

对象：
负责内容团队的营销负责人

已知信息：
用户提供的材料显示，团队方案经常反复修改

假设：
他可能不只在意生成速度，还在意判断标准是否清晰、
协作过程是否可控

可能相关的动机：
时间、控制感、能力认可

替代解释：
产品定位不明确
老板与团队目标不一致
缺少真实客户信息

验证方式：
查看被否决的方案及反馈
询问具体修改原因

状态：
尚未验证

这比：

控制感 0.92，成就感 0.87。

有用得多。

因为后者看似精确，却没有说明这些数字从哪里来。

3. 跨域联想必须比较结构，而不只匹配词语

黄金礼品与外交赠礼可能都涉及“关系表达”。

但“有共同词语”不意味着两者可以直接等同。

Agent 还要比较：

谁在赠送？
谁在接受？
双方权力和关系是否对等？
表达的是什么？
有什么制度和场合限制？
哪部分可以类比，哪部分不能？

所以，真正有价值的不是：

发现两个领域都包含“尊重”。

而是：

发现它们在某个具体问题上具有可解释的相似结构，同时知道类比的边界。

七、创意应该如何产生：自主探索，不是强制发散

你的 Agent 至少应当允许几种不同的入口。

从人进入。 谁在什么情境下作出什么决定。

从事件进入。 某件事情是否暴露了一个与业务有关的问题。

从产品机制进入。 产品为什么有效，能否通过演示或实验讲清楚。

从数据进入。 用户行为说明哪里出现了障碍。

从已有内容进入。 哪些表达已经有效，哪些假设需要重新检查。

这些入口之间可以相互切换。

例如，它最初打算研究黄金礼品的文化故事，但发现用户实际要解决的是：

企业客户担心定制效果不确定。

那么更合适的路线可能是：

查看定制案例 → 梳理确认流程 → 展示样品与成品对比 → 降低购买顾虑。

这不是脑洞不够，而是判断更准确。

“思维算子”保留，但按问题调用

换主体、追原因、看后果、换尺度、寻找反例、跨域类比，都可以保留。

但它们的调用理由应该是：

当前方向过于相似，尝试换一个相关角色。

或者：

当前结论只有支持证据，主动寻找反例。

而不是：

每个任务必须执行二十种算子，产生一百个候选。

创意评分也要服从任务

品牌传播可以更重视新鲜度与表达感染力。

产品比较需要重视准确、清晰和决策帮助。

成交环节需要检查证据、风险和行动阻力。

因此：

新奇不是统一目标，合适才是。

“足够远、能回来”可以作为一类内容创意的参考，但不应成为所有营销动作的总评分公式。

八、真正的自主主循环应该是什么

今晚前面最大的结构性问题，是把“思考维度”画成了一条长流水线。

更适合你的运行方式是：

接收用户目标或新信息
        ↓
读取相关业务记忆、任务状态与授权边界
        ↓
判断：现在最重要的问题或信息缺口是什么？
        ↓
选择下一步
研究 / 分析 / 构思 / 验证 / 制作 / 执行 / 必要澄清
        ↓
检查权限、预算和执行条件
        ↓
执行，并观察真实返回结果
        ↓
更新事实、假设、计划和成果
        ↓
继续推进，或交付，或明确说明阻塞

这里唯一固定的是：

行动要有目的，判断要能被证据修正，外部操作要受授权约束。

具体研究路线不固定。

计划必须能被推翻

例如，Agent 原计划是通过讲故事改善转化。

但查看资料以后发现：

产品页面根本没有说清楚交付内容。

它应该改变计划，而不是为了完成原计划，继续生成十个更漂亮的故事。

也必须知道什么时候停

停止条件可以是：

已达到用户要求的交付标准。
新一轮研究没有提供足够新增信息。
关键数据不可获得。
已到预算上限。
下一步需要外部授权。

停下时，要交代完成了什么、哪些判断仍不确定、为什么没有继续。

自主不是无休止地思考，自主包括决定何时已经足够。

九、结合 Codex：这次应该走“原生领域改造”，不是外部营销编排器

OpenAI 对 Codex 的官方说明，把它的核心描述为协调用户、模型和工具的 Agent loop：模型提出工具调用，运行系统执行并把结果送回模型，循环继续，直到交付或需要用户参与。这正是你要继承的工作机制。

但你要改变的，不只是名字或开场提示。

要改的是它理解工作环境、组织上下文、使用工具、保存认知、管理任务与评估成果的方式。

│ 按需使用的营销方法                  │
│ 原生工具注册与执行                  │
│ 证据、权限、预算和交付检查          │
│ 任务恢复、用户纠偏、结果记录        │
└───────────────────────────────────┘
        │
        ▼
业务工作区、资料、数据库、浏览器、
数据分析环境及获得授权的外部平台

这里没有一个外置的“营销工作流服务”替 Agent 决定先做什么、后做什么。

营销能力直接进入你维护的 Codex 分支。

不过，原生改造仍然需要模块边界。把所有营销逻辑塞进一个巨大的 Rust 文件，不会比模块化更“原生”。

可以在同一个 Rust workspace 中新增领域模块或 crate，编译进自己的运行系统。这是内部工程组织，不是 MCP 服务拼接。

2. 首先改：默认任务身份与工作环境

它的默认工作对象应该从：

仓库、源代码、测试、代码变更。

转向：

业务资料、用户问题、研究证据、营销方案、内容资产和实验结果。

但不应彻底去掉读写文件、执行脚本、数据分析等通用能力。

因为真正负责营销的 Agent，可能需要分析一份表格、处理一批内容、生成网页、检查数据。

去掉“所有任务都当编程任务”的假设，而不是去掉编程能力。

3. 重点改：上下文装配

Codex 官方说明中，模型输入本就由模型指令、开发者指令、项目信息、环境与用户输入等部分组成。因此，你的改造点不应只有一个营销提示词，而应进入上下文构建过程。

你的运行时应该按当前任务装配：

稳定的工作原则
+
当前营销目标
+
当前业务的已知事实
+
相关历史决定
+
尚未解决的问题
+
本轮必要证据
+
授权与预算
+
用户最新要求

而不是每轮把全部画像、全部原语、全部历史资料都塞进去。

关键是：

这一步决策需要什么信息，就提供什么信息。

4. 原生工具：提供行动能力，不把思考拆成假工具

当前 Codex 代码中存在 ToolRouter、ToolRegistry，以及本地执行工具的运行时契约。原生工具执行并不要求通过 MCP；你的分支可以沿这些内部结构增加自己的工具实现。

你的工具更适合围绕实际工作设计：

能力	原生工具负责什么
研究	搜索、读取来源、提取可追溯材料
业务资料	读取授权范围内的产品、客户反馈和历史内容
数据分析	查询数据、运行分析、生成可复查结果
记忆与状态	记录证据、假设、决定，读取相关历史
成果制作	创建和修改脚本、文档、页面、内容资产
外部执行	在授权后发布、发送、更新或运行实验

而“这个时候该换哪个视角”“应不应该继续研究”“是不是不该讲故事”，主要留给主模型结合上下文作判断。

不使用 MCP，不代表不能调用模型 API 或平台 API。区别在于：这些是 Agent 的执行能力，不是替它预排决策的业务流水线。

5. 原生改造应该进入任务与会话生命周期

不应只在开始时注入一次营销提示。

下面这些时刻都需要领域处理：

任务开始时，解析目标、指代、当前业务与允许的行为。

工具返回时，区分观察结果和推断，记录证据来源。

用户纠正时，修改相关假设，并标记依赖旧假设的成果需要复查。

上下文压缩后，保留目标、重要约束、未解决问题和关键证据索引。

任务恢复时，恢复项目状态，而不是只读取聊天摘要。

准备交付或执行时，检查事实、产品能力、授权和版本一致性。

这才是“营销能力进入运行时”，而不是外面套了一层营销页面。

十、营销记忆必须独立于聊天记录，但不能变成另一套后台流程

这里保留前面 MarketingState 的思想，但要修正一个说法：

它不是“世界真相”，而是 Agent 当前对业务的可修正认知。

其中既有事实，也有假设，还有已经被推翻的判断。

1. 至少区分四种内容

用户提供的信息。 例如主营产品、预算、品牌要求。保存来源，必要时仍可核查。

外部观察。 例如网页资料、历史表现、订单数据。

模型假设。 例如“用户可能担心礼物过于贵重”。

经过批准的决定。 例如本轮针对企业周年纪念，不针对婚嫁。

这四种不能混在一起。

尤其不能让模型先猜一个画像，再把自己的猜测当证据，继续推导下一层结论。

2. 品牌、项目、任务、聊天要分开

不建议简单地：

一个品牌 = 一个永远延长的 Thread。

更合理的是：

业务或品牌
    ├── 营销项目
    │      ├── 任务
    │      └── 相关聊天
    └── 长期业务知识与成果

这样，同一品牌可以有多个任务；同一任务也可以在新的聊天中继续。

用户说“现在让你自己营销自己”，系统要识别宣传对象已经切换，不能继续沿用黄金礼品的用户假设。

3. 记录决定的依据，而不是保存一切文字

重要记录应该能回答：

为什么选了这个人群？
哪份材料支持这个观点？
用户在哪一次否定过这种表达？
哪个产品能力已经上线，哪个还只是规划？
哪些内容依赖某条已经被推翻的假设？

这是后续纠偏与复用的基础。

记忆还应有范围：用户说“这条不要讲历史”，不等于永久禁止这个品牌讲历史。

十一、“让它自己卖自己”应当成为一个完整测试，而不只是一个创意题

这个案例需要重新拆开。

第一关：理解“自己”指什么

系统应明确：

当前宣传对象是你开发的营销 Agent 产品。

不是基础模型，不是 OpenAI，也不是一个抽象的“AI 助手”。

第二关：掌握自己的真实产品信息

它需要一份真实、可更新的产品能力记录：

已经实现什么。
哪些功能还没实现。
需要用户提供什么资料。
可以自主执行到什么程度。
有哪些限制。
有什么真实案例或测试结果。

否则它很容易营销一个自己想象中的产品。

第三关：不预设用户一定缺创意

潜在问题可能是选题不足，也可能是：

不知道怎么判断好坏。
团队反复返工。
缺乏事实研究。
内容与成交链路脱节。
不知道失败后应该改哪里。

Agent 应根据证据选择，不应自动落到“通用 LLM 不会营销，所以买我”。

第四关：选择最有说服力的表达

它可以选择一个类比，但也可以判断：

这个产品更需要实际演示。

例如设计一个演示任务：

给出一个陌生业务，只提供有限信息，展示系统如何识别未知、研究、提出备选解释、接受纠偏，最后交付可用方案。

这里最有价值的内容，可能就是 Agent 工作过程本身。

自己卖自己，不一定要找到一个漂亮的故事；也可能是准确地展示自己为什么有用。

第五关：不虚构效果

“可以生成方案”与“能提升销售”不是一回事。

没有真实数据时，不应编造增长比例、客户评价或转化效果。

这项测试要同时考核：

指代理解、产品自知、营销诊断、策略选择和事实约束。

它很重要，但单独通过它，仍不足以证明全面泛化。

十二、Chat 的技术实现与权限：自主，但可控制

Codex 当前 app-server 提供会话启动与恢复、任务启动、进行中追加输入 turn/steer、中断 turn/interrupt，以及流式消息和工具进度。这些能力可以作为你聊天交互的基础，不需要让用户通过功能面板来控制每个步骤。

你的客户端应重点支持：

边工作边补充要求。
中断当前路线。
对具体成果提出修改。
恢复未完成任务。
查看证据与交付物。
批准或拒绝外部动作。

前后端之间沿用 app-server 通信，不等于套壳。关键是它连接的是你改造后的运行系统，而不是外部固定流程。开发时应锁定 Codex 版本，并从该版本生成协议类型，而不是依赖口头记忆中的接口清单；官方也提供对应的 TypeScript 和 JSON Schema 生成方式。

自主权必须有明确边界

研究、分析、在工作区创建草稿，可以在给定范围内自主完成。

发布内容、发送消息、调整价格、花广告费、修改线上资源，则应经过明确授权或事先设定的额度与规则。

并且：

把工具写进 Rust，不意味着外部副作用就自动安全。

Codex 的官方安全设计区分沙箱限制与审批机制；你的营销工具还需要单独落实平台权限、资金限制和副作用检查，不能把代码执行沙箱当成所有业务操作的完整保护。

还有两条应从第一版就加入：

外部资料是数据，不是命令。 网页中的文字不能指挥 Agent 泄露信息或改变权限。

已经批准的内容发生实质修改后，原批准不能自动沿用。 发布对象、内容版本、平台和预算要对应同一次授权。

真正专业的 Agent，不是敢做一切，而是知道自己被授权做什么。

十三、怎样判断它不是“换个提示词的套壳”

不要靠架构名称判断，靠测试。

建议至少比较三种版本：

同一个模型直接接受营销提示。
同一个模型加固定营销流程。
你的原生 Agent。

在尽可能相近的信息和资源条件下，观察差异。

核心测试不是“哪篇文案更漂亮”

应该测试这些行为：

测试	合格表现
换行业	不依赖礼品文化模板，能理解新的产品与购买逻辑
信息不足	标注未知，提出合理假设，不编造确定画像
错误线索	能查证并放弃一个很好讲但不成立的故事
用户纠偏	改变路线，并修正相关状态和成果
不适合叙事	能选择演示、数据、流程改进或其他动作
长任务恢复	知道做到哪里、缺什么、接下来为何这样做
自我营销	使用真实产品能力，而不是虚构优势
外部执行	在授权、版本、预算范围内操作

泛化测试要包含没参与提示调试的行业和任务。

除了黄金礼品、榴莲和营销 Agent，也可以使用工业零件、普通日用品、本地服务、企业软件等差异较大的业务。

并且，同一个行业要测试不同目的：

品牌表达、产品比较、获客诊断、成交改善、内容修改。

否则它可能只是学会了：

任何行业都生成一篇跨领域品牌故事。

那仍然不是你要的泛化。

学习要从真实结果来，不要从自我评分里闭环

模型说一条创意“9.3 分”，只能算评审意见，不能算市场结果。

用户喜欢、内容被采用、获得关注、形成有效咨询、最终成交，也应分别记录。

一条内容曝光高，不足以证明某个“原语”导致了效果。

你的系统应该逐步积累的是：

在什么业务、什么人群、什么渠道、什么条件下，做了什么，观察到了什么；这个结论还有哪些不确定性。

而不是把一次表现写成永久有效的营销法则。

十四、真正的开发顺序：先做一个能完整办事的 Agent

这次我不建议先搭二十个“营销引擎”，也不建议先做十个业务面板。

第一阶段：建立原生 Chat 任务闭环

先让用户能够通过聊天交代任务，Agent 可以读取资料、研究、制作成果、接受中途纠正和恢复任务。

营销工作区、任务状态、证据记录和权限边界同时建立。

这一阶段默认以只读研究和本地草稿为主，不急着开放外部发布。

第二阶段：把营销理解与自主探索放进去

加入业务理解、角色与场景、动机假设、备选解释、按需探索和策略选择。

但每次迭代都用具体任务验证：

是否真的改善了任务？
是否引入了不必要步骤？
换行业后是否还成立？

不要因为新增了一个概念，就给它新建一套必须执行的流程。

第三阶段：做好完整交付与纠偏

不只输出“十个方向”，而是能把选定方向继续推进到用户需要的成果。

例如：

研究 → 选择方向 → 形成完整脚本 → 核查 → 根据反馈修改 → 保存交付。

这只是一个可能的实际任务路径，不是所有任务的固定模板。

尤其要完成“上游事实变化，相关成果需要更新”的处理。

第四阶段：加入有限、可审计的执行能力

从一个明确平台、一类明确动作开始。

执行前能预览，执行中能记录，失败后能区分未执行、部分执行和执行成功，避免重复发送或重复花费。

第五阶段：加入结果观察与策略修正

让 Agent 不只是记住“发过什么”，还知道原目标是什么、结果怎样、下一次应该检验什么。

先学会可靠地修正自己的假设，再谈长期自主优化。

先完整承担一件小事，比同时拥有二十个命名宏大的模块更重要。

最后，把今晚的共识收束成一份真正能指导开发的定义

你的产品应该是：

一个以 Chat 为主入口、基于开源 Codex 原生改造的专业营销 Agent。

用户用自然语言交代业务、目标和限制，系统自主决定需要理解什么、研究什么、尝试什么，并在新证据或用户反馈出现后改变计划。

它可以用人群、场景、动机、因果、事件、视角、信念等方法思考，但不被固定顺序束缚；可以讲故事，也可以判断这次更需要演示、证明、交易设计或数据分析。

它保存可追溯、可修正的业务认知，产出真正可使用的成果，在授权范围内采取行动，并用实际结果检验自己的判断。

所以，今晚最值得定下来的，不是再增加一个“终极营销内核”名称，而是这个分工：

用户负责目标与边界。
Agent 负责选择方法和推进工作。
运行系统负责记忆、执行、权限与可追溯性。
证据负责纠偏，结果负责检验。

你不是要把营销软件改成聊天界面，而是要让一个能够自主工作的 Agent，真正学会承担营销任务。
